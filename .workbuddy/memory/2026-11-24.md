## E2E 端到端验收（11-24，真实栈）

**E2E 发现并修复一个真实缺陷（P1 引入）**：`BrowserViewer/index.tsx` 的 painter 创建 effect 用了空依赖数组，而 `<canvas>` 是条件渲染的（连接中/错误态为占位符）——首帧时 `canvasRef.current` 为 null，effect 直接 return，之后**永不重建**，`painterRef` 恒为 null，所有二进制帧被静默丢弃，表现是「帧到达但画面全黑」。修复：改为在 `paintBlobFrame` 内按需懒创建，并记录 painter 绑定的 canvas 元素，元素变化时 dispose+重建；卸载时统一 dispose。修复后 UI 层实测 canvas 544x360、38400 采样点全部不透明、297 种颜色。

**Stage A（服务端 + 真实 Chrome + 真实 WS，无任何 mock）**：
- 初始化链路：`/setup/verify-password` → `/setup/database`(sqlite) → `/setup/initial-admin` → `/auth/login` 全通
- `stream_mode=screencast`，首帧 0.13s；meta 1024x768；seq 单调连续、增量恒为 1（无丢帧）
- 稳态 15.4 FPS @1024x768，1.91KB/帧（注意：此 FPS 受 headless 软件光栅限制，同链路在 756x413 可达 57.8 FPS，非 relay 限流所致）
- 静态页 2.5s → **0 帧**（无变化不出帧，UI 层同样为 0）
- 输入→重绘→回显 13/14 次：median 7.3ms，p90 12.7ms，max 13.9ms（隔离法：hover 变色页，只有真实重绘才出帧）
- cursor 回显：auto ↔ pointer 正确切换，字段名是 `cursor`（不是 value）

**Stage B（真实 Chrome 渲染 dashboard SPA）**：注入 WS 探针在页面自身 socket 上计数 → 44 帧 / 5.7s、1379KB、`stream_mode=screencast`（无 poll 回退），canvas 真实绘制，无页面错误 → **PASS**（连续两轮稳定）。

**环境坑（重要，后续复用）**：
- 应用启动 Chrome **不带 `--no-sandbox`**（macOS 上 `_should_disable_sandbox()` 返回 False），本沙箱沙箱初始化失败 → Chrome FATAL 退出 → CDP 无响应 → 报 `failed to attach browser profile 'user-1': did not receive a valid HTTP response`。解法：服务端加 `BROWSER_USE_NO_SANDBOX=1`。
- `_normalize_nav_url` 会把 `data:` URL 改写成 `https://data:...` 导致导航失败 → E2E 必须用本地 HTTP 页面（`.e2e-pages/` + `python3 -m http.server 9096`）。
- 首次启动服务需 wizard 密码（`$OCTOP_HOME/octop-login.txt`）+ 绑定数据库后 `database_bound` 才为 true；`setup/status` 可判幂等。
- 安全删除锁 `SAFE_DELETE_BULK_GUARD_ERROR state lock timeout` 会全局阻断删除，导致 tempfile 无法探测临时目录 → **pytest 完全无法启动**（`No usable temporary directory found`）；锁释放后自动恢复。同时 Vite `build` 因 emptyOutDir 调 rmSync 失败 → 用 `--outDir .e2e-buildN --emptyOutDir false` 再 `cp` 覆盖到 `src/octop/dashboard/`。
- dashboard 首次进入会有 onboarding 弹窗需关（点「稍后再说」）；远程浏览器页需要点「启动浏览器」才建会话（非自动）。

## 修复「优化后点击/悬浮错位」（11-24，坐标空间缺陷）

**根因**：P1 screencast 化后指针坐标仍按 `canvas.width` 反推。poll 模式下截图 == 视口，等式成立；screencast 模式下 `canvas.width` 是**解码帧**尺寸，被自适应档位缩放（实测 544×360 帧 vs 1088×720 视口 = 2.0×；756×413 vs 1024×768 = 1.35×/1.86×）。后果：点击落点向左上收缩 → input 永不聚焦；hover 的 `elementFromPoint` 命中错误元素 → cursor 回显停在 auto；宽高比不匹配（1.83 vs 1.33）叠加 `object-fit: contain` 信箱位移 → 偏移进一步放大，且交互触发降级时误差翻倍。

**修复（建立独立"远程视口坐标系"）**：
1. `browserCanvas.ts` 新增 `ViewportSize`；`getCanvasCoords(canvas, e, viewport)` 用 viewport 反算并**补偿 contain 信箱位移**（scale = min(rect/vp)，减居中偏移，再 clamp），无 viewport 时保留旧逻辑兜底（RemoteAndroid 不受影响）。
2. `sizeBackingStore()`：canvas 后备缓冲**恒等于视口**，帧按目标尺寸缩放绘制 → 坐标空间与档位解耦（`createScreencastPainter(canvas, initialViewport)` + `setViewport()`；`paintBase64JpegToCanvas` 同样接收 viewport）。
3. `useBrowserViewController` 提升 `viewport` state（connect 时 set，并用每帧 meta `w/h` 校正，±2px 容差避免闪清）；两个调用点透传 `remoteViewport`。
4. `BrowserViewer` 用 ResizeObserver 把 canvas **元素盒**按视口宽高比精确摆放（`flex:0 0 auto; margin:auto`），让 contain 变成恒等变换；指针 hook 新增可选 `viewport`（ref 读取，保持回调稳定不丢 pointer capture）。
5. 光标回显：`scroll` 也会刷新（滚轮换元素但鼠标没动，否则 cursor 长期停留在旧值）。
6. **顺带修掉一个真 bug**：`should_adjust()` 原来用 `_superseded`（fps 上限丢帧）判定降级——那是限流在做分内事，不是客户端跟不上。动画页面 60fps 推送 + 30fps 上限 → 每秒约 30 次 supersede → 约 1.3s 下一档、7s 到底（15fps/q40/×0.5）且永不回升。改为用 `_push()` 里 **WS send 耗时超帧预算** 计 `_backpressure`；`_coalesced` 仅观测。`take_stats` 增加 coalesced/backpressure。

**验证**：后端 `tests/unit/api` 408 passed；`tests/e2e/browser_stream` 9 passed（含新增 `focus.html` + `test_viewport_coordinates_reach_the_right_element`：只有视口中心是 input，靠 cursor 回显证明服务端命中的元素正确）；前端 `canvasCoords.test.ts` 9 项（半尺寸帧/信箱补偿/边界 clamp/后备缓冲=视口/poll 绘制）+ screencastPainter 2 项，`src/utils`+`src/hooks` 81 passed；`tsc -b` 0；ruff/eslint 无新增问题。前端全量 vitest 26 失败均为 Chat/Sidebar/Skills/Models 等无关模块（无一引用本次改动文件，属既有失败）。
